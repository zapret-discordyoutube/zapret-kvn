# Protocol runtimes and original errors

The source layout on both platforms is documented in [SOURCE_LAYOUT.md](SOURCE_LAYOUT.md). The folder migration is complete; WG/AWG transport validation and the combined stable release are separate gates.

## Architecture basis (owner decision 2026-11-04)

Each protocol runs on its own complete native core, so that everything works as correctly as possible. sing-box is only the intermediary gasket: the owner of TUN, routing, DNS and protected sockets, and the glue between the native cores and the system. Do not reimplement or approximate a protocol in sing-box or in app code when its native core exists. More native cores will be added over time, one per protocol that needs it; a new core is a new protocol owner behind the same gasket, not a replacement for sing-box. The Xray and Hysteria helper processes on Windows are deliberate.

The transport owner is fixed on both platforms: VLESS, VMess and Trojan go to the official Xray core (owner decision 2026-11-16: sing-box has no XHTTP for them and only approximated the rest), Hysteria2 to the official Hysteria core, WG/AWG to the official Amnezia device/netstack, and the remaining protocols to sing-box. Plain WG uses Amnezia with AWG extensions absent. The only routing, DNS and TUN owner on both platforms is sing-box. Its active native JSON owns domain rules and geosite-derived native `.srs` rule sets in both proxy and TUN modes. Xray and Hysteria implement only the selected proxy transport, never a second routing policy. Core selection is not a capability probe or an automatic fallback between protocol implementations.

Protocol adapters retain the original imported URI. Xray needs native JSON, so its adapter translates the URI at that boundary; it must not translate it through sing-box first. On Android the cores are embedded libraries behind the same outbound interface; sing-box owns the only TUN and protected sockets.

Legacy Windows Xray-front and tun2socks selections migrate to sing-box. Existing raw Xray configuration files are retained, not translated or overwritten. Auto connect is disabled during that migration: users must review their sing-box rules before explicitly reconnecting. Existing sing-box users keep auto connect.

## IPv6 to the VPN server first (owner decision 2026-11-22)

A server's IPv4 address is often blocked by address while its IPv6 address still works. With the setting «IPv6 к серверу первым» (Settings → network, on by default) and a native global IPv6 address on the PC's uplink (`xray_fluent/network/server_family.py`, adapter data only, no probe), each core gets IPv6 first in its own native way:

- sing-box native outbounds: `domain_resolver: {server, strategy: prefer_ipv6}` (`_ensure_proxy_server_bootstrap_contract`); sing-box races IPv6, then IPv4 after 300 ms or at once on failure. WG endpoints are unchanged.
- Xray (hybrid, dialed by sing-box through the protect inbound): app `resolve` rules on the protect inbound with `network: tcp` and `strategy: prefer_ipv6` for every server name; the direct outbound races the families. UDP keeps its previous order (one socket, no way back).
- Core patch `core-patches/address-family-memory.patch` (same `common/familymemory` as Android 0020): the family that last worked for a server name starts first; cleared on a network change and after 30 minutes.
- Hysteria2 (`hysteria.exe` with a pinned address): IPv6 pinned first when the start verifies the server; no authentication within 4 s (or all probes failing earlier) restarts the attempt pinned to IPv4 and remembers the IPv6 failure in `server_family.MEMORY` (reset on a network change).
- Latency probes: one family per temporary core (Xray `UseIP` used to pick at random among both families), with IPv6 first the native race (Xray `happyEyeballs`, sing-box `prefer_ipv6`); the Hysteria probe pins IPv6 only once IPv6 has worked for that server.
- Amnezia (WG/AWG, `zapret-amnezia.exe`, one peer): the app resolves the peer and passes the preferred family as `address` (from `server_family.MEMORY`, IPv6 when nothing is remembered) and the other family as `race_address`. The helper's bind (`runtime/amnezia/family_race.go`, same code as Android patch 0021) sends the first handshake to both; the server answers one copy (the second is a replay for it) and the bind keeps that family for the session. Unanswered retries alternate families, so a family that loses only the replies cannot win every time. The helper reports only the family (`address_family` event, never the address) and the app remembers it. No added delay and no restart, unlike the Hysteria2 fallback.
- Not changed: slot helper processes, Xray standalone mode (Go's own RFC 6555 dial with the system resolver order).

## WARP as the entry hop to our server (owner decision 2026-11-25)

Device -> Cloudflare WARP -> our server -> internet. The provider sees only Cloudflare, never the server address (Hiddify's "Proxy unblocker", improved). Setting «Вход через Cloudflare WARP» (Settings -> network), off by default, applied at the next connect. The same design as Android (`android/docs/ARCHITECTURE.md`).

- Everything stays in sing-box, the gasket: WARP is the core's `warp` endpoint. Core patch `core-patches/warp-entry-profile.patch` (same code as Android 0022) gives it the tunnel `mtu` (the app uses 1330: Hysteria2 sends 1252 byte payloads, a 1300 byte packet over IPv6 that does not fit in 1280; packet arithmetic, not yet measured in the tunnel), `profile.cache_path` (a private file in `data/` with the Cloudflare account, reused on restart instead of registering a device) and the account's assigned address as the default peer (the host name resolves to a different edge address each time and some did not answer in field tests).
- `xray_fluent/engines/singbox/warp_entry.py` edits only the runtime config, after planning (`apply_warp_entry` in `runtime_planner.py`, run again after the service slots are attached), without any change to a native core: sing-box native outbounds get a `detour` to the hop, including the connection pool's servers, which live in the provider file (`plan.provider_payload`) and not in `outbounds`; the Xray protect-inbound rule `-> direct` leads into the hop; under the TUN the process rules of the Hysteria helper and of the slot helpers (`process_path: <exe> -> direct`) lead into it as well. (The Hysteria rule is the 0.8.110 one; the slot helpers' rule, `action: route`, is unit-checked but not yet proven on a live run with a real server.) Hysteria and Xray stay official and unpatched.
- Local relays never enter the hop: the sing-box front reaches every helper process through a loopback SOCKS outbound (`127.0.0.1:<relay>`); the helper behind it is the one that dials out. A loopback `server` is not chained (`_is_loopback`); chaining it sent the relay traffic to loopback on the far side of WARP (found in the real plan of 0.8.110, fixed in 0.8.111).
- Owner rule: WARP is an ENTRY only, never an exit and never a server to pick. The guard `violations` allows exactly a server's `detour` (config and pool), the endpoint's own tag and the helper rules in their exact planner shape (`process_path`/`inbound`/`outbound`, `action: route` only); anything else (selector member, other rule, `route.final`, user JSON) stops the plan. Direct traffic never enters WARP.
- Helpers that dial with their own sockets (Hysteria, slot helpers) enter only under the TUN, where their sockets are captured and the process rules apply. In the proxy mode nothing captures them, so the plan is refused with a message (`WARP_ENTRY_NEEDS_TUN`) instead of showing the server address. Not covered yet, refused the same way: WireGuard/AmneziaWG nodes (the helper binds its UDP socket to the physical interface). Pings and speed tests start temporary cores that dial the server directly, so with the hop on they are not made and the reason is shown (`network/entry_hop.py`); the probe of the active proxy runs inside the live core and enters through the hop by itself.
- Verified on real components (2026-11-25, win10): a pool-file outbound with `detour` to the endpoint dials through the real WARP (`endpoint/warp[kvn-warp-entry]: outbound connection to ...`, Cloudflare answered).
- App-side registration (0.8.113, owner decision 2026-11-25): on some networks the provider resets the registration request to the Cloudflare API (field report: `wsarecv: An existing connection was forcibly closed by the remote host`), and without an account the hop never starts. `xray_fluent/network/warp_registration.py` registers the account itself before planning (`_ensure_warp_account_steps`, called first in `start_proxy_steps` and `start_tun_steps`) and writes the file the core reads (`profile.cache_path`), so the core never calls the API. Routes: the plain request, the same with the TLS ClientHello cut into two TCP segments inside the server name, and both for every other address of the API host. If all fail, this launch runs WITHOUT the hop (a visible message says the server address is seen once), and when the connection is up the account is registered through the local HTTP proxy of the running VPN (`proxy_url`), after which the app reconnects with the hop (`_register_warp_via_vpn_steps`). Verified on win10 with the real API: both direct routes, the through-proxy route (a real sing-box proxy inbound, Windows Python 3.12), and the real core starting WARP from the Python-written file with the API unreachable for it (5/5 DNS answers through WARP). Not verified: a network that really resets the request.
- Server names resolve outside the tunnel (0.8.114, owner's diagnostics 2026-11-26): the hop's WireGuard endpoint resolves a domain destination ITSELF through the router's DNS rules (`dnsRouter.Lookup` in the core), and the template's rules end at the proxied DNS, which waits for the very connection being opened: `lookup <server>: context deadline exceeded`. `apply_entry_hop` therefore puts one DNS rule at the top of `dns.rules` (`{domain: [every name the hop dials], action: route, server: bootstrap-dns}`): the names of chained outbounds (config and pool) and the server names of the Xray sidecar. Verified on win10 with the real planner config, `sing-box.exe` and `xray.exe`: without the rule the hop's lookup hangs (curl 25 s), with it the log shows `dns: match[0] domain=... => route(bootstrap-dns)` and the lookup completes in milliseconds. When the app's IPv6-first `resolve` rule already resolves the name before the hop, the hop dials the address and the rule is not needed; it covers every other case.
- What the app says about the hop (0.8.115, owner request 2026-11-26, "more logs"): per connect with the setting on, `[warp-entry] вход через WARP включён, аккаунт WARP готов` (or the registration route and its time in ms), and 40 s after the connect one line `[warp-entry] итог за 40 с ...` with the handshake retries (ports only, never addresses), the `endpoint not initialized` count, the address-lookup timeouts and the registration errors the real core reported (`network/warp_hop_health.py`, fed from `_on_core_log`). When the tunnel is clearly not coming up (5 refusals or 3 unanswered handshakes) the user is told once, in plain words, that the network may block the WARP UDP ports (2408, 500, 1701, 4500). Verified on win10 with the real controller and cores: the normal chain, and a tunnel pointed at an address nothing answers (`tests/test_app_e2e_warp_entry.py`). The reports service (`docs/CLIENT_REPORTS.md`) refuses unknown fields, so the same facts reach its database only after the receiver admits them (proposal sent to the reports chat 2026-11-26).
- Registration: the account is registered by a plain Go HTTP request of sing-box.exe; with the TUN up it would be captured and routed back toward the hop that waits for it. The hop has `profile.detour` to its own direct outbound `kvn-warp-api`, which leaves on the physical interface directly (same fix as Android, found there first).
- Stalled starts: roughly one start in four never got a handshake answer for the same account (also on the Windows VM). `core-patches/warp-entry-recovery.patch` (same code as Android 0023) probes the started tunnel once and, if it does not open within 4 s, rebuilds the endpoint with a fresh source port and the next of 4 candidates, all literal IPs (assigned v4 on its first port, its second, the first again, then `162.159.192.1`). Bounded, nothing runs afterwards; an explicit address is never rotated.
- Network changes: the registered endpoint is the `warp` wrapper, so `core-patches/warp-entry-interface-update.patch` (same code as Android 0024) forwards the network manager's `InterfaceUpdated` to the inner WireGuard endpoint; without it the tunnel kept its socket on the old network after a switch.
- Log: `[warp-entry] вход через WARP: серверов через вход=N, правил помощников=M` at every start.
- Requires the sing-box.exe built with the patch; the core bundle fingerprint covers `core-patches/` so the next bundle rebuilds it.

## Errors

`xray_fluent/diagnostics/runtime-errors.json` and Android's `app/src/main/resources/runtime-errors.json` are the same catalog. An error is evidence first: component, operation stage, original message, session generation and a target identity only when the producer can prove it. The catalog supplies classification, never replacement prose. Unknown messages remain visible.

The error journal is separate from bounded traffic/debug logs. It retains each distinct error during the application process lifetime and counts repeats. The UI and diagnostic export use this journal without the traffic-log limit. Passwords, private keys, tokens and credential-bearing URIs are redacted. Release verification must exercise real producer, observer, journal and UI/export boundaries; direct reducer tests alone do not verify this contract.

Loopback TCP resets/EOF are retained as `LOCAL_CLIENT_CONNECTION_CLOSED` with `record_only` policy. They cannot consume Hysteria recovery or turn successful HTTPS readiness into a server failure. A real process exit remains terminal; TLS/auth/pin failures retain their higher-priority security classification.

## Source-built sing-box UDP fix

`core-patches/sing-udp.json` pins upstream sing module versions, zip/patch hashes and the packet regression test shared with Android. The private patched module receives complete UDP datagrams in both normal and low-memory builds, reserves transport header space in addition to payload, and uses packet-size buffers for connected UDP read waiters. TCP buffers are unchanged. UDP buffers grow to 64 KiB (plus required header space), so in-flight UDP memory use increases.

The Go cache is never patched in place. An unknown dependency version or changed cached source fails the build. Windows bundle cache keys include adapter source, patches, tests and build tools, not only upstream versions. Android AAR freshness includes `CORE_UDP_PATCH_SHA256`. Remove the patch only after the same full-chain packet tests pass against an upstream fix.

## Coordinated stable preparation

Before validation and the final source commits, run from the Windows checkout:

```bash
python3 scripts/prepare_core_release.py --windows-version 0.5.8 --android-tag v0.3.27
```

Use the next actual unpublished versions. Each new pair checks official upstream tags (Amnezia prereleases allowed), updates the two pins and writes the identical `core-release-freeze.json` to both repositories. Repeating that pair validates the receipt offline, without selecting a newer tag. API/dependency incompatibility must be repaired and tested before committing or publishing; no old-core fallback.

Then run all platform gates, commit/push all ready source and use the existing Windows runner and Android stable publisher. The Windows runner reuses a matching freeze; the Android publisher requires its tagged source to match the freeze. Installed apps receive these built cores with the app update only.

### Partial (delta) app updates

The release signer (`sign_release` in `scripts/release_windows.py`) puts every file of the release ZIP (path, size, SHA-256) into the signed `update-manifest.json`. `xray_fluent/updates/delta_zip.py` uses that list: the updater reads the ZIP central directory by HTTP Range, reuses installed files whose SHA-256 equals the signed one, downloads only the other entries and accepts each of them only if its size, CRC-32 and SHA-256 match the signed list. Any doubt (no Range, other file set, bad hash, more than 60% of the archive) falls back to the whole-ZIP download that is checked against the signed archive SHA-256 as before.

The patched `sing-box.exe` must stay byte-identical when its sources are unchanged, otherwise ~33 MB are downloaded in every update. `build_singbox_front.py` therefore passes the patched `sing` dependency to `go mod edit -replace` as a path relative to the source tree (Go writes that path into the executable) and refuses a binary that embeds its temporary build directory.

### A replaced exe under a running app

PyInstaller reopens the exe by name for every lazy import (`pyimod01_archive.ZlibArchiveReader.extract`). When another file takes that name while the app runs, the next lazy import reads the new file at the old offsets and the app crashes: field check #3 (2026-11-23) found 15 such crashes on 0.8.102-0.8.107 (`crash:error` = `zlib.error` at `extract:134`, `crash:OSError` at `extract:119`), in `start_metrics_worker` and in the disconnect cleanup, often seconds from a failed update on the same install. `main.py` therefore calls `xray_fluent/platform/frozen_archive.install` right after the exception hooks: the archive reader keeps one descriptor to the original file, opened with `FILE_SHARE_DELETE`, so renaming or deleting the exe works as before and imports keep reading this build. The log line `Module archive pinned to the running exe` shows it acted; the first time the name points at another file the app logs `[update] The program file was replaced while running` and notes the app error `update:exe_replaced`, so the program that swaps files under a live app stays visible in the field. Proof: `tests/test_frozen_archive.py` (PyInstaller's own reader crashes unpinned and reads the original pinned; it runs where PyInstaller is installed, as on the build VM) and a frozen onedir probe built with PyInstaller 6.21 on win10 (unpinned: `zlib.error` after the exe was replaced; pinned: the lazy import worked).

## Android audit observations

The existing Hysteria adapter emits `server certificate SHA-256 mismatch` but the old Android classifier required the substring `pin`. It therefore lost the security classification and could show the subsequent generic HTTPS failure as VPN-200. The shared catalog covers the adapter and official executable texts.

The protected domain UDP dialer returns a NAT wrapper that loses the numeric sender address (`127.0.0.1:port` becomes `:port`). A loopback boundary test reproduces this. A local official Hysteria plain handshake and TCP echo still pass through that wrapper, so this is not proof of the reported device failure. Android ADB is currently unavailable; no device reproduction has been claimed.
